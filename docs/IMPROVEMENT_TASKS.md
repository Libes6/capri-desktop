## Как передавать задачи агенту

Передай агенту этот файл и ID одной задачи, например: «Выполни CAPRI-02 по docs/IMPROVEMENT_TASKS.md». Не поручай весь список одним большим изменением.

Перед началом агент должен:

1. Прочитать применимые `AGENTS.md`, проверить `git status`, актуальную ветку и состояние PR #1. Если PR уже смержен, начать от актуального `main`; иначе сохранить зависимость от изменений PR #1.
2. Сверить описанное ниже состояние с исходниками. Имена новых настроек и файлов в задачах являются предложениями, а не существующим API.
3. Реализовать только выбранную задачу. Не перезаписывать чужие изменения и не повышать версию без отдельного запроса.
4. Использовать существующие Electron, JavaScript, config, IPC и словари. Не переносить приложение на другой стек и не вводить отдельный store или библиотеку настроек без необходимости.
5. Проверить результат по критериям задачи. В отчёте разделять тесты, запуск приложения, визуальную проверку и реальные проверки на ОС.
6. Не мерджить, не публиковать релизы и не менять подпись/секреты без отдельного поручения. Подготовить изменения и сообщить, что проверено.

Общие ограничения:

- Windows x64, Linux x64 и macOS Apple Silicon являются целевыми платформами.
- Linux 0.1 использует X11/XWayland. Нативный Wayland пока не заявлен.
- Текущие переводы: русский, английский, французский, испанский, португальский. Новые UI-тексты добавлять во все существующие словари.
- В общих текстах писать «в системе», «на компьютере». Названия ОС использовать там, где это объясняет конкретное ограничение или действие.
- API-ключи не передавать в renderer, логи, отчёты или URL. Существующая граница main/preload/renderer сохраняется.
- Хуки ассистентов не устанавливать в реальный профиль пользователя ради тестов. Использовать временные каталоги.
- Не решать задачу отключением sandbox/contextIsolation, запуском от root или автоматической выдачей системных разрешений.

## CAPRI-01. Язык системы при первом запуске и понятный fallback

**Приоритет:** P1. **Зависимости:** нет.

**Цель:** приложение само выбирает поддерживаемый язык системы. Если перевода на этот язык нет, использует английский. Пользовательский выбор языка имеет приоритет над автоматическим.

**Текущее состояние:** `config.DEFAULTS.lang` уже равен `auto`; в `src/main/main.js` есть `resolveLang()`, который проверяет предпочитаемые языки и локаль системы. `rendererConfig()` отдаёт `lang` и `langSetting`. Не создавать вторую независимую реализацию выбора языка.

**Работа:**

- Проверить первый запуск с чистым временным профилем и вариант со старым конфигом без `lang`.
- Нормализовать региональные коды, например `ru-RU`, `en_US`, `pt-BR`, до ключей существующих словарей.
- В автоматическом режиме брать первый поддерживаемый язык из системного списка предпочтений; если весь список не поддерживается, брать `en`.
- Сохранять именно режим `auto`, не заменять его вычисленным языком. После перезапуска учитывать изменение языковых предпочтений ОС.
- Явный поддерживаемый выбор пользователя не заменять системным. Неизвестное или удалённое значение в старом конфиге трактовать как `auto`.
- Проверить единый язык меню, реплик, setup, guide и настроек. В режиме Auto показывать текущий вычисленный язык, например «Автоматически: русский».
- Если существующая реализация уже удовлетворяет части требований, сохранить её и исправить только реальные пробелы.

**Файлы:** `src/main/main.js`, `src/main/config.js`, `src/main/labels.js`, `src/renderer/js/lines.js`, `src/renderer/js/app.js`; после CAPRI-04 также экран настроек.

**Готово, когда:** проверены поддерживаемая локаль, региональные варианты, несколько предпочитаемых языков, полностью неподдерживаемый список, пустое/неизвестное значение, явный пользовательский выбор и повторный запуск в Auto. Неподдерживаемая локаль не вызывает падения или смешивания переводов. Результат покрыт тестами выбора языка и ручной проверкой меню/реплик.

**Вне задачи:** автоматический машинный перевод, скачивание языковых пакетов, добавление новых языков, изменение настроек языка самой ОС.

**Проблема:** отдельные пункты уже отключены вне Windows, но UI и guide могут предлагать действия без работающей реализации.

**Работа:**

- Сформировать один небольшой набор доступностей в main и передавать renderer только нужные признаки. Учитывать реальные условия, а не только название ОС, например наличие helper/разрешения/X11.
- Использовать эти признаки в меню, guide, setup и предложениях чата. Не обещать, что действие выполнено, если платформа его не поддерживает.

**Готово, когда:** UI на каждой платформе соответствует реальной реализации; неподдерживаемое действие не вызывает Windows-команду и не выдаёт ложный успех; ограничения локализованы. Проверены обычный путь и отказ функции.

**Вне задачи:** реализация отсутствующих нативных возможностей. Они описаны отдельно в CAPRI-08–10.

## CAPRI-03. Отдельное окно настроек: оболочка и управление окном

**Приоритет:** P1. **Зависимости:** CAPRI-02.

**Цель:** вынести настройки из длинного контекстного меню в отдельное обычное окно, сохранив быстрые действия в трее.

**Работа:**

- Добавить пункт «Настройки…» в существующее меню и отдельное окно с разделами «Общие», «Поведение», «Ассистент и ИИ», «О программе».
- Открывать только один экземпляр. Повторное действие должно показывать существующее окно и передавать ему фокус.
- Окно настроек должно получать мышь и клавиатуру независимо от click-through overlay. Закрытие настроек не закрывает персонажа.
- Использовать существующие стили/шрифты и понятную навигацию. На небольшом экране содержимое прокручивается, элементы доступны с клавиатуры.
- В оболочке не должно быть пустых интерактивных переключателей: перенос самих настроек выполняется следующей задачей.
- В трее сохранить быстрые действия: показать/спрятать, звук, чат, настройки, выход. Не удалять существующие действия до их переноса.

**Файлы:** `src/main/main.js`, `src/main/labels.js`, `src/preload.js`; новые renderer-файлы окна настроек рядом с существующим renderer.

**Готово, когда:** открытие/повторное открытие/закрытие работают; окно не остаётся click-through и не перехватывает ввод после закрытия; Escape/Tab и фокус проверены; окно визуально проверено на Mac и запущено smoke-проверкой на остальных ОС.

**Вне задачи:** переделка внешности персонажа, перенос всех настроек за один PR, новая UI-библиотека.

## CAPRI-04. Настройки: рабочие поля, сохранение и синхронизация

**Приоритет:** P1. **Зависимости:** CAPRI-01, CAPRI-02, CAPRI-03.

**Работа:**

- Перенести существующие настройки: язык, запуск с системой при поддержке, размер, звук/громкость, экран, движение и анимации, отслеживаемый ассистент, выбор ИИ-провайдера.
- Сначала проверить фактические поля `config.js`; не создавать дубликаты тех же настроек под новыми именами.
- Сохранение и применение должны идти через существующий main/config-поток. Меню, окно и overlay должны оставаться синхронизированы.
- Настройки применять сразу там, где это уже поддерживается; для требующих перезапуска честно показывать необходимость перезапуска.
- API-ключ вводить как новое значение, не читать сохранённый секрет из main. Показывать только наличие ключа; ошибки у поля и общая ошибка сохранения должны различаться.
- Старые конфиги должны продолжать работать с defaults. Ошибка записи не должна выглядеть как успешное сохранение.
- Дать «Сбросить настройки» с конкретным описанием области сброса. Не удалять ключи, хуки, историю и память без отдельного явно выбранного действия.

**Файлы:** `src/main/{config,main,setup}.js`, `src/preload.js`, окно настроек, `src/main/labels.js`, `src/renderer/js/lines.js`.

**Готово, когда:** изменение видно сразу, сохраняется после перезапуска, отображается в другом UI; старый конфиг читается; ошибка сохранения видна; неподдерживаемые возможности недоступны; секреты не попадают в renderer или логи.

**Вне задачи:** переработка всех providers и всей системы хранения.

## CAPRI-05. Частота инициативы и защита от повторяющихся реплик

**Приоритет:** P2. **Зависимости:** CAPRI-04 для UI настройки; остальную логику не разносить в конкурирующие изменения тех же файлов.

**Текущее состояние:** `Panel.say()` уже учитывает приоритеты, guide, открытый чат и отложенные сообщения. Не заменять это новой очередью без доказанной необходимости.

**Работа:**

- Добавить настройку инициативы: «Тихо», «Обычно», «Активно». Она управляет необязательными репликами и реакциями, а не важными событиями.
- Определить категории необязательных сообщений и их cooldown. Избегать повтора недавно выбранных вариантов, но корректно работать с наборами из одной реплики.
- Сохранить ошибки, запросы разрешения, напоминания и пользовательские ответы независимо от режима инициативы.
- Не прерывать открытый чат или читаемый ответ ради idle-реплики. Сохранить существующие приоритеты `Panel.say()`.
- Сохранять выбор режима в config. Историю недавно сказанных реплик достаточно держать в памяти процесса.

**Файлы:** `src/renderer/js/{brain,bond,pc,panel,app,util,lines}.js`, `src/main/config.js`, окно настроек.

**Готово, когда:** на воспроизводимой последовательности событий подтверждены разная частота необязательных реплик, отсутствие немедленных повторений, сохранение alerts/reminders и отсутствие вытеснения чата. Добавлены тесты с управляемым временем/выбором реплики там, где это необходимо.

**Вне задачи:** изменение характера персонажа и генерация всех реплик через LLM.

**Текущее состояние:** main уже перевключает overlay после `resume` и `unlock-screen`. Полноценную приостановку декоративной работы нужно проверить и добавить отдельно.

**Работа:**

- Обработать поддерживаемые на целевой ОС события блокировки/разблокировки и сна/пробуждения. Зафиксировать отличия событий Electron между ОС.
- Передавать состояние renderer через узкий IPC. При паузе остановить декоративные циклы и необязательный polling, не разрушая состояние персонажа.
- Не приостанавливать main-процесс целиком: входящие события ассистентов и учёт напоминаний должны сохраняться.
- После возвращения восстанавливать один комплект циклов; не плодить listeners/timers. Не проигрывать все пропущенные декоративные события залпом.
- Сохранить итоговое состояние задач, важные запросы и просроченные напоминания; показывать их после возвращения по существующим правилам приоритета.

**Готово, когда:** проверены несколько циклов блокировки и сна без дублирования таймеров, потерянных важных событий, зависания анимации или click-through. Выполнен повторный замер нагрузки. Тесты событий не выдаются за реальные проверки блокировки на каждой ОС.

**Вне задачи:** отключение системных защит, управление системным сном и изменение настроек ОС.

## CAPRI-08. macOS: исследование и прототип отслеживания окон

**Приоритет:** P2. **Зависимости:** CAPRI-02.

**Цель:** доказать минимальный рабочий способ получать геометрию чужих окон на Apple Silicon до реализации сложных эффектов.

**Работа:**

- Изучить текущий контракт `startWindowWatch()` и формат `{ fg, wins, taskbar, ai, game, usb, plug }`. Не требовать реализации всех Windows-полей для первого Mac-прототипа.
- Проверить доступные нативные macOS API и необходимые разрешения для геометрии, foreground и жизненного цикла окон. Выбрать минимальный поддерживаемый способ интеграции с Electron.
- Собрать изолированный прототип: список подходящих окон, активное окно, координаты, фильтрация собственного overlay.
- Проверить Retina/DIP, несколько мониторов, отрицательные координаты, Spaces, полноэкранное приложение, перемещение/закрытие/сворачивание окна.
- Не отправлять заголовки/содержимое окон в чат, LLM или внешние сервисы. Не включать захват экрана для получения геометрии, если выбранному API он не нужен.
- Если нужно разрешение, объяснить пользователю зачем; не выдавать его автоматически. При отказе сохранить базовый overlay.

**Файлы:** `src/main/windows.js`, `src/main/main.js`; новые Mac helper/адаптер и его packaging-конфигурация только при необходимости.

**Готово, когда:** есть воспроизводимый прототип на Apple Silicon и короткий документ с выбранным API, разрешениями, форматом координат, ограничениями и способом упаковки helper. Если полный нужный набор данных недоступен, это зафиксировано до интеграции.

**Вне задачи:** possession, ревность, чтение содержимого окон и обещание полного Windows-паритета.

## CAPRI-11. Обновление приложения через GitHub Releases

**Приоритет:** P2. **Зависимости:** CAPRI-03/04 (окно настроек), CAPRI-05 (инициатива). Пересекается с CAPRI-06 в `main.js`: правки там держать компактными.

**Цель:** установленный Capri сам узнаёт о новой опубликованной версии форка и обновляется по образцу проекта «Густаф» (`docs/release.md`, `docs/updater-smoke.md`, `UpdateController`): проверка один раз при старте и вручную, явная загрузка, установка только проверенной загрузки и только после подтверждения перезапуска. Никогда не говорить «актуально» без успешной проверки, не запускать операции параллельно.

**Работа:**

- `electron-updater` поверх уже существующего draft-пайплайна: без токенов в приложении, `autoDownload=false`, `autoInstallOnAppQuit=false`, без пререлизов. Обновляется только упакованное приложение; dev и smoke — `disabled` с причиной.
- Проверить по исходникам `GitHubProvider`, как выбирается релиз и разбирается версия при теге `fork-vX.Y.Z` (унаследованные теги автора `v0.1.0…v0.4.4` заняты). Выбор provider обосновать и покрыть тестом.
- Windows NSIS: скачать → «Обновить и перезапустить». Linux: AppImage обновляется, `.deb` только сообщает о версии и даёт ссылку на страницу релиза. macOS без Developer ID: проверить, примет ли Squirrel.Mac ad-hoc-подписанное обновление; если нет — собственная проверенная замена bundle, как у Tauri-апдейтера Густафа, с откатом; ссылка на страницу только когда bundle нельзя заменить (DMG, App Translocation, нет прав).
- electron-builder выдаёт `latest.yml`, `latest-linux.yml`, `latest-mac.yml` и `.blockmap` с `--publish never`; `draft-release.js` загружает их в draft и проверяет имена и sha512; `build.yml` передаёт их в артефакты. Подпись, секреты и автопубликацию не добавлять.
- UI в «О программе»: версия, статус, предлагаемая версия, заметки релиза plain text, прогресс, кнопки. Пункт трея «Доступно обновление X…». Одна необязательная реплика через инициативу. IPC — узкие каналы settings-preload с проверкой `settings.owns`. Тексты во всех пяти словарях.
- Локальная проверка: две тестовые сборки mac (0.1.0 и 0.1.1) из изолированной копии и loopback-feed, доступный только тестовой сборке.

**Файлы:** `src/main/updates.js`, `src/main/mac-update.js`, `src/main/main.js`, `src/main/settings-{view,window}.js`, `src/settings-preload.js`, `src/renderer/js/{settings,app,lines}.js`, `src/main/labels.js`, `package.json`, `scripts/draft-release.js`, `scripts/updater-smoke.js`, `.github/workflows/build.yml`, `docs/UPDATES.md`, тесты.

**Готово, когда:** тесты контроллера (нет версии, есть версия, сеть ≠ «актуально», sha512, двойные вызовы, dev/deb/AppImage/mac) и draft-release с yml проходят; `npm test` и `npm run test:smoke` зелёные; `docs/UPDATES.md` описывает provider/тег, поведение по ОС, отличия от Густафа и ручную проверку. Реальная установка на каждой ОС после публикации отмечена как непроверенная, пока её не выполнили.

**Вне задачи:** подпись обновлений отдельным ключом (нужны секреты), Developer ID/нотаризация, Authenticode, обновление `.deb` из приложения, публикация релиза.

## Общая проверка после реализации

- `npm test` для логики и контрактов, затронутых задачей.
- `npm run test:smoke` для изменений запуска, окна, IPC и renderer bootstrap.
- Целевая сборка, если меняются зависимости, native helper, ресурсы, пути упаковки или CI.
- Ручная UI-проверка для окон, текстов, настроек и поведения. Для простых текстовых правок не добавлять тесты, зеркалящие каждую строку словаря.
- Для нативных функций проверка на реальной целевой ОС обязательна; моки и зелёная упаковка её не заменяют.
- В итоговом сообщении агента: что сделано, какие файлы изменены, что проверено, что осталось непроверенным. Не повышать степень подтверждения результата.
